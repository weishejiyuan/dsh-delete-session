# Spec：会话永久删除

Status: ready-for-agent
Date: 2026-11-19
ADRs: 0000–0006

## Problem Statement

DSH 桌面端的会话只能归档，不能真正删除。归档把会话从视野里移走，但会话日志仍完整留在磁盘上，用户没有任何清理手段。DSH 没有暴露会话删除 API，用户唯一能做的只有归档，磁盘上的旧会话越积越多。

更糟的是「看起来删了」和「真的删了」之间没有界限：归档会让会话从侧栏消失，用户无法判断它是否还占空间，也无法判断它是否还能被搜索到。

## Solution

在会话栏给每个会话行提供两个「永久删除」入口——行内 hover 按钮和右键菜单项。点击后弹一个确认框，说明会永久删除哪个会话、此操作不可撤销；确认后会话目录被递归删除，同时清理它在 workspace registry 里的归档与置顶标记，搜索索引由 DSH 自己的对账机制收敛。

保护措施针对两种真实损坏风险：正在运行的会话不允许删除（避免删坏正在写入的日志），当前正在查看的会话不允许删除（避免视图指向一个不存在的会话）。两者都在按钮层就置灰并说明原因，不让用户走完两次点击才被拒绝。

删除是不可逆的，不提供撤销窗口，也不自动替用户切到另一个会话。

## User Stories

1. As a DSH 桌面端用户，我想在会话行的 hover 按钮条里看到一个删除按钮，这样我不用打开右键菜单就能直接清理会话。
2. As a DSH 桌面端用户，我想把鼠标停在删除按钮上 500ms 后看到「永久删除」的说明，这样我能确认这个按钮是删不是归档。
3. As a DSH 桌面端用户，我想在会话行右键菜单里也找到一个「永久删除」项，这样我可以从已有习惯的入口操作。
4. As a DSH 桌面端用户，我想看到「永久删除」项排在归档项之后、并且上方有一条分隔线，这样我不会在点归档时误点到删除。
5. As a DSH 桌面端用户，我想让「永久删除」项带危险色渲染，这样我能一眼看出它是破坏性操作。
6. As a DSH 桌面端用户，我想在点删除后看到一个确认框，这样我不会因为手滑而永久丢掉一个会话。
7. As a DSH 桌面端用户，我想在确认框里看到被删会话的标题，这样我能确认删的是我以为的那个会话。
8. As a DSH 桌面端用户，我想在确认框里看到「此操作不可撤销」的说明，这样我对后果有明确预期。
9. As a DSH 桌面端用户，我想让确认框的「取消」在左、「永久删除」在右，这样它与 DSH 其他对话框的位置一致，我不会点错。
10. As a DSH 桌面端用户，我想在点取消后什么都不发生（会话还在、没有提示打扰），这样我改变主意时没有副作用。
11. As a DSH 桌面端用户，我想在确认删除后看到会话从侧栏消失，这样我确认操作生效了。
12. As a DSH 桌面端用户，我想在删除成功后看到一条「会话已永久删除」的提示，这样我知道该操作已完成而不需要自己去核对。
13. As a DSH 桌面端用户，我想让被删会话的磁盘目录真正消失，这样释放的空间是真实的释放。
14. As a DSH 桌面端用户，我想让被删会话的归档标记和置顶标记一起消失，这样侧栏不会因为一条找不到会话的残留标记而出现异常。
15. As a DSH 桌面端用户，我想在删完一个会话后搜索不到它，这样搜索结果不会出现点不开的死会话。
16. As a DSH 桌面端用户，我想让正在生成回复的会话的删除入口置灰，这样我不会误删一个正在写入的日志。
17. As a DSH 桌面端用户，我想在鼠标停在置灰的删除入口上时看到「会话正在运行，请先停止」，这样我知道该先做什么。
18. As a DSH 桌面端用户，我想在该任务结束后删除入口自动恢复可点，这样我不需要刷新页面。
19. As a DSH 桌面端用户，我想在删掉当前会话后由 DSH 自己收敛视图，这样插件不替我决定下一个看什么。
    _（2026-11-19 修订：原为「当前会话入口置灰保护视图」，已撤销；视图短暂失效由 DSH 会话侦测处理。）_
20. As a DSH 桌面端用户，我想让**当前正在查看的会话也能删**（只要它没在运行），这样只剩最后一个会话时我不会被卡住。
    _（2026-11-19 修订：原为「当前会话入口置灰并提示不能删除」，因只剩一个会话时会永久不可删而撤销。）_
21. As a DSH 桌面端用户，我想在已归档的会话上也看到删除入口，这样我清理归档区时不用「先取消归档、再删除」两步。
22. As a DSH 桌面端用户，我想在还没发过消息的空白会话行上看不到删除入口，这样我不会去点一个必然失败的按钮。
23. As a DSH 桌面端用户，我想在后台还有子任务或定时任务时被阻止删除，即使界面上的「正在运行」标志已经变成 false，这样我不会删掉一个表面空闲但实际活跃的会话。
24. As a DSH 桌面端用户，我想在删除被阻止时看到具体原因而不是笼统的「失败」，这样我知道下一步该做什么。
25. As a DSH 桌面端用户，我想在对一个已经不存在的会话执行删除时看到「会话不存在，可能已被删除」，这样我不会困惑于一个沉默的失败。
26. As a DSH 桌面端用户，我想在删除遇到文件系统错误时看到失败原因，这样我能判断是不是权限或占用问题。
27. As a DSH 桌面端用户，我想让删除操作要么整体成功要么整体失败，这样我不必猜它删到哪一步了。
28. As a DSH 桌面端用户，我想在删除后不被自动切换到别的会话，这样我的注意力不会被替我做的决定打断。
29. As a DSH 桌面端用户，我想在删除后没有「撤销」按钮，这样我不会误以为会话还留在某个地方。
30. As a DSH 桌面端用户，我想在 diff 面板之类的面板激活状态下也能删除普通会话，这样我不会因为打开了面板就失去清理能力。
31. As a DSH 桌面端用户，我想在装了本插件后现有插件全部照常工作，这样我不用为了一个删除功能牺牲别的功能。
32. As a DSH 桌面端用户，我想在禁用或卸载本插件后所有删除入口都干净消失、DSH 其余功能不受影响，这样我可以随时回滚。
33. As a DSH 桌面端用户，我想在中文和英文界面下都看到正确文案，这样我用哪种语言都没有半截翻译。
34. As a DSH 桌面端用户，我想在插件市场里看到这个插件的图标和名称，这样我能认出它。
35. As a DSH 维护者，我想让删除入口的破坏性行为被自动化测试覆盖，这样改动后我能立刻知道有没有删坏东西。

## Implementation Decisions

**插件形态**：Profile bundle，单个 npm 包，Host 半 + Client 半共享同一版本号。Loader 配置里只挂载一个 Host 行；Client 半由 DSH 的客户端模块系统扫描包的清单字段后自动加载，不额外挂行。

**Host 半运行形态**：普通 ESM 模块，在真实 Node 环境运行，可用 Node 内置 API。它注入 web server、connection、workspace registry、session persistence 四个服务。

**Client 半运行形态**：不是 ESM 模块，而是浏览器模块系统要求的工厂包——脚本加载时即向全局模块加载器注册一个工厂，依赖通过该工厂收到的同步 `require` 取得（React 与 UI 组件库由 web shell 内置提供）。不引入打包器，手写工厂包装，用 `React.createElement` 表达结构。

**删除是四步，顺序不可交换**：
1. 活动检查——询问宿主所有活动提供方该会话是否仍有未停止的工作，非空则中止，不触碰文件系统。
2. 递归删除——用宿主持久化层的 `stat(id)` 拿到该会话日志的绝对路径，取所在目录后递归删除；再用配置的 sessions 根做围栏，目标目录不在根内则拒绝。
3. 清归档集合——把该 id 从 registry 全局归档集合移除。
4. 清置顶集合——把该 id 从 registry 全局置顶集合移除。

**活动检查复用宿主机制**：用宿主已有的会话活动询问事件，与官方归档走同一个闸门。这正是「表面空闲但仍有子 agent / 后台 job / 定时任务」能被拦住的原因。

**全或不全**：所有匹配目录都删完才返回成功；任一目录删除失败即整体失败，不做部分成功报告，也不回滚已删目录（删除本身幂等）。

**不加锁**：不引入去重集合或锁文件。并发保护由活动闸门、删除的幂等性、以及宿主持久化层自带的跨进程写锁共同承担。

**索引不手工清理**：查询索引是对账式的，宿主会在下一次对账时自动丢弃已不存在的会话行。插件碰它会与实现机制对抗。

**API 契约**：单一端点，单 method，无版本前缀。请求体含会话 id。响应体统一为「成功布尔 + 机器可读 code + 可选人类可读信息」。四个业务 code：成功、会话运行中、会话不存在、删除失败。HTTP 状态与 code 一一对应（成功 200、运行中 409、不存在 404、失败 500）。另有四道前置守卫的 code：方法不允许 405、请求被拒 401·403、路径不存在 404、参数错误 400。

**鉴权**：复用宿主的同源放行判定，不接方法级权限门。

**sessions 根目录可注入**：默认取用户主目录下的 DSH sessions 路径（`$DSH_HOME` → `~/.dsh`，再拼 `sessions`），允许通过插件配置覆盖。用途是**围栏**而不是定位：定位由 `stat(id)` 负责，根只决定「找到的目录是否允许被删」。这一条同时服务测试与「DSH home 不在默认位置」的用户。

**行可见性矩阵**（唯一来源见 ADR-0000 与 0003/0004）：

| 行的状态 | 行内按钮 | 右键菜单项 |
|---|---|---|
| 普通会话 | 显示、可点 | 显示、可点 |
| 当前会话（未在运行） | 显示、**可点** | 显示、**可点** |
| 运行中会话 | 显示、置灰 | 显示、置灰 |
| 已归档 | 显示、可点 | 显示、可点 |
| 空白（未落盘） | 不渲染 | 不出现 |
| 面板激活态 | 与其他状态同规则 | 与其他状态同规则 |

优先级：空白 → 不渲染；运行中 → 置灰；其余 → 可点。**2026-11-19 修订：撤销「当前会话置灰」**，理由是只剩一个会话时该入口会永久不可用，而官方 `archiveSession` 本身也不拦当前会话（ADR-0004「修订 2026-11-19」）。

**客户端 / 服务端的分工**：客户端的「运行中」只看轮次状态，窄；服务端的活动检查看子 agent / job / schedule，全。窄的放客户端做提前提示，全的放服务端做权威兜底，两者不互相替代。

**确认框**：挂在全窗口浮层 slot。按钮顺序与官方归档确认框一致——取消在左、确认在右。确认按钮是描边样式 + 红色文字（不是实心红块），与官方视觉统一。

**文案**：内联在客户端代码里的单一字典，不建独立 locale 文件（避免两份副本发散）。命名空间独立，只提供中英两套。key 按用途分段：标签、确认框、失败提示。

**命名**：右键菜单项与图标槽位 key 同名但分属不同命名空间；locale 命名空间另取一名，三者刻意不重名。菜单项排在官方归档项之后，并带「上方分隔线」与「危险」两个标志。

**冲突约束**：占用侧栏会话行按钮区与全窗口浮层两个 slot；不占用任何已被现有插件使用的 slot 名、菜单 id、图标 key、locale 命名空间或路由前缀。

## Testing Decisions

**唯一 seam：Host 的 HTTP 端点。** 不对客户端 UI 做自动化测试，也不新增内部函数级 seam。

**为什么选这一层**：这个插件全部的数据损坏风险都在 Host 半——递归删除正在写入的目录、留下 registry 孤儿、部分成功导致状态不一致。UI 层的最坏情况是按钮显示不对，不会毁数据。测最高风险处，投入产出比最高。同时端点契约（四个业务 code + 四道守卫 code、请求/响应体）已经在上面定死，是稳定外部契约，不会因为内部重构而失效。

**好测试的标准**：只驱动外部契约，不断言内部实现。具体地——给端点一个真实的临时目录树和一个假的宿主上下文，调用端点，然后断言「磁盘上还剩什么」「返回了哪个 code」「registry 的清理方法被调用了几次」。不断言「用了哪个函数删目录」「内部有几层调用」。

**覆盖的行为**：
- 普通会话 → 成功码，日志文件与其所在目录一起消失，归档与置顶清理各被调用一次
- 目录名不由插件假设：`stat` 指向哪个目录就删哪个目录
- 未落盘的 pending 会话（`stat` 快照无 `location`）→ 不存在码，磁盘未动
- 目录在配置的 sessions 根之外 → 失败码，磁盘未动
- 活动检查非空 → 运行中码，磁盘完全未被触碰，registry 清理未被调用
- `stat` 返回 `undefined` → 不存在码
- 删除过程抛错 → 失败码，且带上可读原因
- 非 POST 方法 → 方法不允许
- 鉴权判定拒绝 → 拒绝码，不进入删除逻辑
- 缺会话 id 或 id 为空 → 参数错误码

**测试技术选择**：Node 内置测试运行器 + 断言库，零依赖。理由与「不引入打包器」一致——这个包的体积和复杂度不值得引入测试框架。临时目录用系统临时区 + 用后清理，避免污染真实 DSH 数据。

**prior art**：本仓库此前没有代码也没有测试，官方安装包在生产分发包里不带测试文件，因此没有可直接复用的本地测试范式。本 spec 自行建立最小范式：一个测试文件 + 临时目录 + 假上下文。

**客户端验证方式**：靠验收清单人工核对（见下）。这不是偷懒——为一个 8 字符串、两个按钮、一个对话框的 UI 搭 jsdom + 假模块加载器 + 假种子模块 require 的装置，测得的是胶水代码而不是真实渲染行为，维护成本高于它拦住的问题。

### 修订 2026-11-19（实现期，用户批准）

上文「唯一 seam：Host 端点，不对客户端 UI 做自动化测试，也不新增内部函数级 seam」在实现时被放宽，理由是用户选了「只写代码 + 自动化测试、不安装不重启 DSH」的验证策略（决策 A）——没有真机可依赖时，人工验收清单一个人都跑不了，代码就完全裸奔。具体改动：

- **客户端 UI 也有自动化测试**，但**不引入 jsdom、不引入测试框架**：用 Node 桩件模拟 `window.__ModuleLoader__` 拿工厂 → 传桩 `require`（假 React、假 primitives）→ 假 ctx → 直接调用组件函数并传假 props（`useSessions`/`usePanelInfo` 是标准 props，本来就能从外部注入）。覆盖的是槽位注册参数、可见性矩阵、确认框交互与失败文案映射；**仍不断言真实渲染结果**，视觉与交互手感仍归人工验收。
- **新增两个 Host 内部 seam**：`createDeleteHandler(ctx, config, {rm})`（`rm` 可注入，否则无法可靠触发删除失败路径——`force: true` 会吞掉 ENOENT）与 `resolveSessionsRoot(config)`（配置优先级单测需要）。二者仅导出给测试，路由层仍只用端点契约。
- **测试期模块解析垫片**：`test/stub-resolve.mjs` + `test/schemastery-stub.js`，用 `node:module` 的 `registerHooks` 精确重定向 `@deepseek-ai/schemastery`（该包只在 DSH 安装树里可解析）。**生产代码不为测试让步**，垫片只在 `npm test` 时生效。
- **未变**：下面的人工验收清单仍然有效且**尚未执行**，任何自动化测试不得被引用为人工验收项的通过证据。

> **2026-11-20 补记**：上条的「尚未执行」已不再成立——插件已装真机，用户确认大部分验收项可用，验收阶段据此结束。取证边界见代码仓库 `docs/manual-acceptance.md`：逐条留证的只有 3 项（A3/B16/A8），其余为用户确认通过但未逐条留证。**「自动化测试不得作为人工验收通过证据」这条原则不变。**

**人工验收清单**（装好后逐条打勾）：
1. 会话行 hover 出现 trash 图标按钮，Tooltip 显示「永久删除」
2. 右键菜单底部出现「永久删除」项，带分隔线与危险色
3. 当前正在查看的会话（未在运行）入口可点；删掉它后该行消失、视图由 DSH 自行收敛，不报错
4. 运行中会话的入口置灰，任务结束后自动恢复
5. 点入口弹出确认框，含会话标题与不可撤销说明
6. 确认框「取消」在左、「永久删除」在右，后者为红色文字描边样式
7. 点取消无任何副作用、无提示
8. 确认后会话从侧栏消失、出现成功提示
9. 删除后磁盘目录消失、搜索不到
10. 已归档会话可正常删除
11. 空白新会话行没有删除入口
12. 面板激活态下普通会话仍可删除
13. 禁用插件后入口全部消失，DSH 其余功能正常

## Out of Scope

- **批量/多选删除**：原需求未提，会引入选择态与批量确认的 UI 复杂度
- **撤销窗口 / 回收站**：「永久删除」的语义就是不可恢复；加撤销会稀释确认框的警示作用
- **删除后自动切换到另一个会话**：不替用户决定下一个看什么
- **删除 workspace**：与本插件无关，宿主已有该能力
- **强制停止运行中任务后删除**：删除不等于终止任务，两件事应分开；用户先停止再删
- **手工清理查询索引**：索引对账式自清理
- **远程 / 多 peer 权限控制**：桌面单用户场景下方法级权限门是零收益复杂度
- **自定义删除后行为（脚本钩子、通知外部系统等）**：原需求未提
- **命令行或 API 方式删除会话**：只做 UI 入口

## Further Notes

**验收的先后顺序建议**：先跑自动化测试（验证 Host 逻辑），再装插件跑人工清单（验证 UI）。反过来的话，UI 出问题时难以判断是 Host 逻辑错还是接线错。

**安装与回滚**：安装用插件 CLI 的本地链接方式挂到 desktop profile，重启 DSH 生效。回滚用对应 remove 或直接移除插件目录后重启。本插件不修改任何 DSH 持久化结构，回滚无残留数据——这是刻意的设计，避免「删插件还要清残留」。

**已知残余窗口**：客户端「运行中」标志看不到子 agent / 后台 job / 定时任务。因此存在「按钮可点、点完被服务端拒绝」的短窗口。这不是缺陷，是两层判定的必然结果；服务端会给出明确原因，用户不会遇到沉默失败。

**若 DSH 未来提供官方删除 API**：应改用官方 API，本插件相应 ADR 作废。当前走文件系统是「宿主没给别的路」的结果，不是偏好。

**风险最高的两处改动**（将来维护时优先回归）：一是删除顺序（活动检查必须在文件操作之前），二是 registry 清理的两个调用（漏一个就留孤儿，且短期内看不出来，只在「仅看已归档」或置顶区才暴露）。
